# catch-up

セッション(スレッド)を始めるときに、現状を把握する skill。[wrap-up](../wrap-up/README.md) と対になる。

前のセッションやほかの人が残した引き継ぎ(Issue・PR のコメント・docs・TODO)と、開いている Issue・PR を読み、現状をまとめて次のタスクを提案する。Issue か PR の番号を渡すと、その中身と関係するコード・docs を把握し、計画を提案して、実装の前で止まる。

## 前提

- git リポジトリで使うことを想定している(git でなければ、git まわりの確認は飛ばす)
- Issue・PR を読むには、[GitHub CLI](https://cli.github.com/)(`gh`)がインストール・認証済みであること(なければ、その確認は飛ばす)

## 使い方

```
/catch-up
/catch-up #12
```

「全体を把握して次のタスクを提案して」「前回どこまで進めた?」「#12 対応を進めます。Issue 内容とプロジェクト全体を把握してください」のような依頼でも起動する。ただし、起動するかどうかは Claude が依頼の意図から判断するので、確実に動かしたいときは `/catch-up` で呼ぶ。

## 引数

| 引数 | 意味 |
|---|---|
| なし | プロジェクト全体の現状を把握し、次のタスクを提案する |
| `#N`(`N` や URL でもよい) | その Issue か PR を把握する。Issue か PR かは自動で見分ける |
| その他 | 「影響範囲も見て」「docs は見なくていい」などのメモ。既定の動きより優先される |

## 主な挙動

- **読むだけで、何も変えない。** コミット・push・ブランチの作成や切り替え・ファイルの編集・Issue や PR への投稿はしない。例外は、リモートのブランチの情報を最新にする `git fetch --prune` だけ
- **引数なし:**
  - リポジトリの状態(今のブランチ・未コミットの変更・stash・未 push のコミット・worktree)と、既定ブランチの最近の履歴を見る。前のセッションの残りがあっても、報告するだけで触らない
  - 開いている PR(レビューの状況・未対応のコメント・CI・最新のコメント)、開いている Issue、TODO.md など、`docs/` の最近の変更を読む。Issue・PR が多いとき(20 件ほどを超えるとき)は、すべてのタイトルと、最近更新された 10 件の中身を読む
  - 現状と次のタスクの候補をまとめ、おすすめを 1 つ挙げて、どれに取りかかるかを聞く。選んだものは、`#N` を渡したときと同じように把握する
- **Issue の `#N`:**
  - Issue の本文・コメント・関係する PR や Issue を読み、作業がもう始まっていないか(その Issue を参照する PR や、ブランチ)も確かめる
  - プロジェクトのルールと、仕様にあたる docs を読んだうえで、Issue が関わるコード・テスト・docs を読み、影響範囲を洗い出す
  - Issue の要点・今の実装(`ファイル:行` 付き)・影響範囲・コミットできる単位での手順・ブランチ名の案・決めることを、計画としてまとめる。方向性の判断はユーザーに聞き、細部は自分で決めて一覧にする
  - ブランチは作らない。計画が承認されてから作る
- **PR の `#N`:** PR の説明・コミット・レビューの状況とコメント(インラインのものも)・CI・コンフリクト・ローカルのブランチの状態を読み、どこまで進んでいて次に何をするかをまとめる。マージを自分から勧めることはしない(マージはユーザーが決める)
- **最後は止まる。** 計画が明らかに見えても、実装には入らない。ユーザーの指示を待つ

まとめは、結論(次に何をするか)から書き、見出しと短い箇条書きにする。候補には番号ではなく短い名前を付け、番号と中身を突き合わせなくても読めるようにする。読んで分かったことと推測は分けて書き、確かめられなかったことも書く。

まとめ・計画・質問は、必ず指定された言語で書く。言語は、ユーザーの設定や指示(`language` 設定・CLAUDE.md・プロジェクトのルールなど)で指定されたものを使い、指定がなければユーザーが書いている言語に合わせる。SKILL.md が英語でも、それにつられて英語にはしない。

挙動の詳細は [SKILL.md](SKILL.md) を参照。
