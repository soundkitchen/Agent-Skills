# you-are-a-reviewer

セッションをレビュー担当(レビュアー)にする skill。他のセッションから届いたレビュー依頼を、Claude Code 組み込みの `code-review` skill でレビューし、結果を依頼元のセッションへ返す。

依頼する側の skill [request-review](../request-review/README.md) と組で使う。2 つを組み合わせたレビューの流れは、request-review の README を参照。

## 前提

- Claude Code のセッション間メッセージ(`SendMessage` / `ListAgents`)が使えること。依頼元とレビュアーは、同じマシン上の別セッションとして動かす
- Claude Code 組み込みの `code-review` skill
- [GitHub CLI](https://cli.github.com/)(`gh`)がインストール・認証済みであること
- レビュアーのセッションを、レビュー対象と同じリポジトリの clone(または worktree)で起動すること。PR の最新コミットを `git fetch` して読むため
- リポジトリが GitHub にあること(`pull/<番号>/head` の ref を使う)

## 使い方

レビュー担当にするセッションを、名前を付けて別に立ち上げる。依頼元は `ListAgents` に出るセッション名で依頼先を指定するので、`skill-reviewer` のような分かりやすい名前にしておく。

```sh
claude -n skill-reviewer
```

そのセッションで、次のように起動する。

```
/you-are-a-reviewer medium --comment
```

起動すると待機状態になり、依頼が届くたびにレビューして結果を返す。自分から勝手には起動しない(`/you-are-a-reviewer` と打ったときだけ動く)。

セッション名について:

- 起動後に名前を付ける・変える場合は、`/rename skill-reviewer` を使う
- 同じ名前のセッションがすでに動いていると、名前の後ろに自動で文字列が付く(例: `skill-reviewer-graceful-unicorn`)。レビュアーを起動し直すときは、古いセッションを終了してから起動する。そうしないと、依頼元が名前で見つけられない
- skill の中から Claude がセッション名を付けることはできないので、名前はユーザーが付ける

## 引数

引数は `code-review` と同じもの。レビューのたびに既定のオプションとして使う。

| 引数 | 意味 |
|---|---|
| `low` / `medium` / `high` / `xhigh` / `max` | code-review のレベル。省略すると、起動時にどのレベルにするか聞かれる |
| `--comment` | 指摘を PR にインラインコメントとして投稿する。あわせて、レビューの結果(LGTM か、指摘がいくつ解決したか)も PR にコメントする |
| `ultra` | 非対応。ユーザーだけが起動できる課金のクラウドレビューで、結果も後から届くため。起動時に指定すると別のレベルを聞かれる |
| `--fix` | 非対応。レビュアーは読むだけで、修正は依頼元が行う。指定されても外してレビューする |

依頼文でレベルやフラグを指定すると、その依頼では既定より優先される。

## 主な挙動

- **レビュー対象は常に PR。** PR 番号・URL・ブランチ・パスで依頼されても、PR に解決してからレビューする。PR が特定できない場合や、依頼元の手元にしかない変更(未コミット・未 push)の場合は、レビューせずに依頼元へ問い合わせる
- **レビュアーの作業ツリーは変更しない。** PR の最新コミットは `refs/pr/<番号>` に fetch し、周りのファイルもそこから読む
- **2 回目以降(再レビュー)は、前回までの指摘に絞って確認する。** code-review は実行せず、指摘ごとに解消したかを返す。前回レビューしたコミット以降に、指摘と関係ない変更(LGTM 後の機能追加など)があれば、その部分だけ code-review する
- **依頼元が理由を添えて「直さない」とした指摘は、** 理由に納得できれば「対応しない(合意)」として閉じる
- **マージの通知のような通知では、** レビューせず、その PR のレビューを終わったものとして扱う。マージの通知なら、その PR の `refs/pr/<番号>` を消す。レビューの依頼かどうか分からないメッセージには、レビューせずに依頼元へ問い合わせる
- **結果は、必ず指定された言語で返す。** 要約、使った引数、レビューした PR のコミット、指摘の全文を含む。言語は、ユーザーの設定や指示(`language` 設定・CLAUDE.md・プロジェクトのルールなど)で指定されたものを使い、指定がなければ依頼文の言語に合わせる。ユーザーへの報告も同じ
- **PR に投稿するのは、`--comment` のときだけ。** 投稿するのは次の 2 つで、`--comment` がなければ何も投稿せず、結果は依頼元へのメッセージだけで返す
  - **code-review の投稿**:指摘のインラインコメント(と、code-review が付けるまとめ)。code-review に任せる
  - **結果のコメント**:レビュアーが `gh pr comment` で投稿する。最初のレビューでも再レビューでも、指摘の有無にかかわらず、レビューのたびに投稿する。依頼元に返事をする前に投稿し、投稿に失敗したら返事でそう伝える。レビュアーからであること、LGTM か(指摘の数や、再レビューなら指摘ごとの状況)、レビューした head のコミットを書く。1 行目には、言語によらない決まった目印 `<!-- you-are-a-reviewer:result -->` を入れる(GitHub の画面には出ない)。作者と同じアカウントでも、作者のコメントと見分けられるようにするため。依頼元のセッションや、次のセッションの [catch-up](../catch-up/README.md) が、PR からレビューの状況を読めるようにするため。レビュアーと作者が同じ GitHub アカウントだと approve できないので、その代わりにもなる。目印は誰でも書けるので、catch-up はリポジトリのオーナー・メンバー・コラボレーターか、自分の `gh` のアカウントが書いたものだけを結果として読む
  - approve・変更の要求・スレッドの resolve はしない
  - グローバルやプロジェクトの CLAUDE.md に「レビュー結果は必ず PR に投稿する」といったルールがあっても、この skill の指示が優先される。それ以外のプロジェクトのルール(CLAUDE.md・AGENTS.md など)には従う

挙動の詳細は [SKILL.md](SKILL.md) を参照。

## 注意

- `refs/pr/<番号>` が消えるのは、マージの通知を受けたときだけ。GitHub の画面や別のセッションでマージした PR、マージせずに閉じた PR の ref は、レビュアーの clone に残る。残っても実害はほとんどない(普段の `git log` や `git branch` には出ない)が、まとめて消すなら、レビュー中でないときに `git for-each-ref --format='%(refname)' refs/pr/ | grep -E '^refs/pr/[0-9]+$' | xargs -n 1 git update-ref -d` を実行する(名前が番号の ref だけを消す)。`+refs/pull/*/head:refs/pr/*` のように `refs/pr/` へ書き込む fetch の設定があるリポジトリでは、その ref も消えるので使わない
- 依頼元とレビュアーのセッションで権限モードが違うと、依頼メッセージがユーザーの承認待ちで止まることがある
- skill を更新しても、すでに起動しているレビュアーは古い内容のまま動き続ける。反映するには、そのセッションで `/you-are-a-reviewer` を呼び出し直すか、セッションを起動し直す。起動し直したレビュアーは前回までのレビューの記録を持たないが、依頼元が前回の指摘と前回レビューしたコミットを添えれば、再レビューとして扱う
